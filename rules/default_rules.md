# Default Rules — 사람용 문서

이 문서는 `loop_harness`에서 동작하는 AI 에이전트(Claude, Codex 등)에게 적용되는 기본 규칙을 사람이 읽기 위해 정리한 것이다.
AI가 실제로 읽는 지시문은 프로젝트 루트의 `AGENTS.md`이며, 두 문서는 같은 규칙을 각 독자에 맞게 서술한다.

**규칙마다 공통 식별자(예: `LOG-001`)를 붙이며, 규칙을 바꿀 때는 이 문서와 `AGENTS.md`에서 같은 식별자의 항목을 함께 수정한다.** 두 문서가 어긋나면 AI는 `AGENTS.md`를 따르고 불일치를 보고한다.

## Identity. 기록 주체

- 에이전트는 자신의 이름(`claude` 또는 `codex`)과 실제 사용 모델을 기록한다. 실제 모델을 확인할 수 없으면 `unknown`이며 추측하지 않는다.
- Harness가 작성한 템플릿 답변은 `ai: harness`, `model: none`으로 기록한다. 에이전트가 자신의 답변에 이 신원을 사용하면 안 된다.
- 호출자 답변의 모델은 호출자 자신의 실제 모델이다. 자식 CLI에 요청한 모델이 호출자의 모델을 증명하지 않는다.
- `model: none`은 `ai: harness` 전용이다. claude/codex는 실제 모델 또는 `unknown`을 사용하며 저장기와 요청 검증에서도 none을 거부한다.

## LAY-001. 스크립트 저장 위치

- 프로젝트의 모든 스크립트는 아래의 단일 예외를 제외하고 프로젝트 루트의 `modules/` 아래에 저장한다. 테스트 스크립트와 명령 실행 진입점도 포함한다.
- 프로젝트 루트의 `install.sh`만 설치 진입점으로 예외 허용한다. 이를 지원하는 구현은 `modules/` 아래에 둔다. 이 예외는 `Makefile`이나 다른 루트 진입점에는 적용하지 않는다.
- 기능별로 `modules/harness/`, `modules/harness/adapters/` 같은 하위 디렉터리에 묶는다. 테스트 스크립트는 `modules/tests/`에 둔다.
- 공통 대화 저장기는 `modules/save_dialog.py`다. 공개 가이드와 로컬 전용 milestone 문서는 `docs/`에 두고 SHR-001에 따라 검토한 공개 가이드만 공유한다. 대화 기록은 프로젝트 루트의 `dialog/`에 둔다.
- 호출자가 관리하는 승인 registry, 실행 권한 추적 기록, 사용자 메시지 출처 파일은 프로젝트 루트의 `approvals/`에 둔다. 기존 대화 출처는 `dialog/`에 유지하고, 호출별 원본 스냅샷은 harness가 관리하는 실행 증거·상태와 함께 프로젝트 루트의 `runs/<run_id>/`에 둔다. 두 위치는 데이터 디렉터리이며 스크립트 저장 위치가 아니다.
- 승인 기록·출처 파일·실행 기록은 target workspace 밖에 둔다. 파일의 위치나 존재만으로 사용자 승인이 성립하지 않으며 APR-001을 계속 적용한다.

## APR-001. 변경 전 승인

검토·동의와 실제 변경 지시를 구분하고, 파일에 적힌 내용만으로 변경 권한을 추론하지 않는다.

- 검토, 피드백, 의견, 동의 표시는 변경 지시가 아니다. AI는 판단과 "바꾼다면 이렇게"라는 목록까지만 답하고 멈춘다.
- 규칙 문서 수정, 파일 생성, 코드 작성은 사용자가 그 대화에서 명시적으로 승인한 범위 안에서만 한다.
- 규칙 문서에 이미 적혀 있다고 해서 승인된 것이 아니다. 승인되지 않은 변경임을 알면 그렇게 말한다.
- 현재 승인된 방식의 대화 기록(LOG-001)은 변경이 아니므로 계속한다.
- 작업 승인과 실행 권한은 별개다. 사용자 원문은 한정된 작업을 승인하고, 샌드박스·도구 권한은 특정 실행 환경이나 명령을 허용한다. 서로를 대신하지 않으며, 실행 권한이 필요하다는 이유로 이미 받은 작업 승인을 다시 요청하지 않는다.
- 별도 권한 확인이 필요한 실행은 호출자가 권한 요청 전에 `approvals/<task-id>/permission-trace.jsonl`에 요청 항목을 남기고, 이후 관찰 결과를 추가한다. 사용자 원문·출처, 승인 범위나 승인 파일, 정확한 명령·작업 디렉터리, 요청 권한 모드·이유, 확인 가능한 도구 참조를 연결한다. 비밀 정보는 제외하고 생략 사실을 표시한다. 결정과 결과는 관찰된 것만 기록하고, 승인 UI의 선택을 알 수 없으면 `unknown`으로 남긴다. 명령 성공만으로 사용자가 팝업을 승인했다고 단정하지 않는다.
- 권한 추적 기록은 호출자가 관리하는 보조 근거로, harness 승인 JSON 스키마와 분리한다. 파일 존재만으로 권한이 생기지 않는다. 새 항목을 추가하는 방식으로 기록하고 기존 승인·대화는 보존한다. 앞선 도구 결과를 나중에 정리한 기록은 소급 정리임을 표시한다. 새 기록 의무는 이후 실행부터 적용하며, 과거 추적 기록이 없다는 이유로 미승인 실행이라고 판단하지 않는다.

## LOG-001. 대화 기록 저장

### 목적

하네스는 Claude와 Codex를 번갈아 호출한다. 어느 질문에 누가 무엇이라고 답했는지를 사람이 나중에 추적할 수 있어야 한다.

### 파일 단위: 질문/답변 한 쌍 = 파일 하나

답변마다 새 파일을 만든다. 기존 파일에 이어 쓰지 않는다. 파일 번호만 보면 어느 도구가 답했든 기록 순서를 읽을 수 있고, 두 도구가 같은 파일에 쓰는 일이 없다.

```
dialog/dialog_YYMMDD_NNNN.txt
```

| 부분 | 의미 |
|---|---|
| `YYMMDD` | 기록 생성일, Asia/Seoul 기준 |
| `NNNN` | 그 날짜의 공통 순번, 4자리. 모든 도구가 같은 번호 공간을 쓴다. 기록 생성 순서이며 질문 접수 순서와 다를 수 있다 |

번호 정책: **성공적으로 확정된 기록에는 날짜별 연속 번호를 부여한다. 확정 전 실패는 번호를 소비하지 않는다. 기존 번호의 공백을 발견하면 이상으로 보고하며, 원본 확인 없이 기존 기록의 번호를 바꾸거나 대체 기록을 생성하지 않는다.**

| 상황 | 처리 |
|---|---|
| 0003까지 저장했고 다음 기록이 확정 전에 실패 | 재시도 성공 시 0004 |
| 0004는 저장됐지만 성공 응답 전달에 실패 | 같은 call_id의 재시도에는 기존 0004 반환 |
| 0004가 사라지고 0005는 존재 | 저장기가 경고를 출력. 사람이 원인을 확인하고 복구. 자동 재번호화나 빈 기록으로 메우기 금지 |
| 두 기록이 동시에 저장됨 | 저장기가 잠금으로 직렬화해 0004, 0005로 배정 |

번호가 연속이라고 대화가 모두 저장되었다는 뜻은 아니다. 저장 호출 자체가 빠지면 공백도 생기지 않는다. 하네스에서는 call_id와 저장 완료 상태로 누락 여부를 확인한다.

### 저장 방법: 공통 저장기

AI가 파일을 직접 쓰지 않고 `modules/save_dialog.py`를 호출한다. 번호 배정, 형식, 시간대, 덮어쓰기 방지를 한 곳에서 처리하기 위해서다.

저장 위치는 현재 디렉터리와 무관하게 항상 프로젝트 루트(`modules/`의 상위)의 `dialog/`다. 하위 디렉터리에서 실행해도 같은 곳에 같은 번호 공간으로 저장된다. 다른 위치는 `--dialog-dir`로 명시할 때만 쓴다.

```
python3 <프로젝트 루트>/modules/save_dialog.py --ai claude --model <모델> \
  --question-file q.txt --answer-file a.txt --call-id <기록 id> [--asked "YYYY-MM-DD HH:MM"] [--run-id <id>]
```

저장기의 동작:

| 상황 | 처리 |
|---|---|
| 번호 배정 | `dialog/.lock` 잠금 안에서 오늘 최대 번호 + 1. 동시 호출은 직렬화되어 연속 번호를 받음 |
| 권한 부족, 디스크 오류 등 | 원인을 출력하고 종료 코드 1로 실패. 번호를 소비하지 않음 |
| 저장 도중 중단 | 임시 파일에 먼저 쓰고 fsync 후 원자적으로 이름을 확정하므로 일부만 쓰인 기록 파일은 남지 않음 |
| 확정 뒤 임시 파일 정리 실패 | 기록은 이미 확정된 것이므로 경고만 출력하고 종료 코드 0 |
| 같은 `call_id`로 재호출 (내용 동일) | 기존 파일 경로를 돌려주고 새로 만들지 않음. 날짜가 바뀌어도 모든 파일에서 찾으므로 자정 이후 재시도에도 중복이 없음 |
| 같은 `call_id`, 다른 내용 | 종료 코드 2로 거부. 아무것도 쓰지 않음. "내용"은 ai, model, run_id, 질문, 답변이며 시각은 제외 |
| 중복 확인 중 기존 파일을 읽지 못함 | "기록 없음"이 아니라 "확인 불가"로 보고 종료 코드 1. 아무것도 쓰지 않음 |
| `[RECORD]`로 시작하는데 헤더가 끊겼거나 필수 필드가 없음 | 구버전 파일과 구분해 "손상된 기록"으로 보고 파일명을 명시하며 종료 코드 1. 아무것도 쓰지 않음. 복구는 사람이 한다 |
| `call_id` 누락, 빈 문자열, 여러 줄, 허용 문자 외, 128자 초과 | 저장 전에 거부, 종료 코드 1 |
| 본문에 `[RECORD]`, `call_id:`, 구분선 등 로그 형식이 들어 있음 | 메타데이터는 파일 맨 위 고정 구역에만 있고 파서는 그 구역만 읽으므로 오인하지 않음 |
| 저장 실패 | 답변은 보존하고 같은 `call_id`로 저장만 다시 시도. 기록 실패 때문에 모델을 다시 실행하지 않음 |

### 파일 내용

메타데이터가 먼저 오고 본문이 뒤따른다. 본문에 어떤 문자열이 있어도 메타데이터로 오인되지 않게 하기 위한 배치다. 아래는 실제 기록이 아닌 형식 설명이며 꺾쇠·날짜 표기는 자리표시자다.

```
================================================================================
[RECORD]
ai: claude
model: <실제 모델 ID 또는 unknown>
asked: YYYY-MM-DD HH:MM +09:00 또는 unknown
saved: YYYY-MM-DD HH:MM +09:00
call_id: <call-id>
content_id: <hash>
--------------------------------------------------------------------------------
[QUESTION]
(사용자 질문 원문)
--------------------------------------------------------------------------------
[ANSWER]
(답변 전문)
================================================================================
```

- `asked`: 질문 접수 시각. 모르면 `unknown`. `saved`: 저장 시각. 둘 다 Asia/Seoul(+09:00).
- `ai`: 실제 답변한 에이전트 또는 `harness`. `model`: 사용한 모델. 알 수 없으면 `unknown`; 모델 없이 만든 harness 템플릿 답변은 `none`. 추측하지 않는다.
- `run_id`: harness 답변과 기존 caller 인계의 실행 ID다. 새 공유 caller 대화는 인계의 `dialog_run_id`가 null이며 저장 시 `--run-id`를 생략한다. 기존 인계의 dialog_run_id가 있으면 유지한다. 공통 call_id는 모든 저장 재시도에서 그대로 사용한다.
- `call_id`: 기록 식별자, 필수. 한 줄, 1~128자, 허용 문자는 영숫자와 `. _ : -`. 하네스에서는 하네스가 부여하고, 수동 대화에서는 AI가 첫 저장 시도 전에 하나 만들어 재시도 내내 같은 값을 쓴다. `content_id`는 저장기가 ai, model, run_id, 질문, 답변에서 계산해 기록한다.
- 질문과 답변은 바이트 그대로 저장한다. 끝 줄바꿈도 바꾸지 않는다. 각 구분선 앞의 줄바꿈 하나는 저장기가 넣는 구분자이며 본문이 아니다.
- 저장된 답변 전문과 사용자에게 전달한 답변은 같아야 한다. AI는 답변 본문을 확정한 뒤 그 본문을 저장하고 그대로 전달하며, 저장 경로는 답변 뒤에 `saved: <경로>` 한 줄로 따로 표시한다. 이 줄은 실행 정보이며 답변의 일부가 아니다.
- 도구 호출 로그는 제외한다.
- 도구의 실행 권한 질문·결과는 APR-001의 추적 기록에 둔다. 이를 별도의 사용자 Q/A로 만들어 저장하거나 사용자 질문 원문에 섞지 않는다. 실제로 따로 받은 사용자 메시지는 구분하며, 필요하면 최종 답변에서 권한 추적 기록을 링크한다.

### 승인된 기록 담당 주체

새 loop 승인에는 `dialog_owner: harness | caller`, `report_identity`, `caller_dialog`를 명시한다. Caller의 caller_dialog는 `{message_id, call_id}`, harness는 null이며 모두 승인 범위에 포함한다. `direct_stdin`·`manual_import`는 입력 경로이므로 기록 책임자를 추론하는 데 사용하지 않는다.

Intake에는 사용자 질문 원문을 그대로 넣고, 다듬은 작업 지시는 `objective`에만 넣는다. 한 질문에 답하기 위해 여러 실행을 수행할 때에는 같은 intake/input_ref와 승인된 caller_dialog를 재사용한다. 공유 call_id는 최종 답변의 식별자이며 각 run_id와 별개다. 서로 다른 사용자 메시지를 텍스트가 같다는 이유로 묶지 않는다.

| 모드 | 기록 담당 |
|---|---|
| 하네스 인계가 없는 수동 대화 | 각 AI가 기존 방식으로 저장기를 호출 |
| `harness` | 하네스가 확정한 최종 답변을 `ai: harness`, `model: none`으로 한 번 저장한다. 사용자에게 그 본문을 그대로 전달하며 같은 질문으로 두 번째 Q/A를 저장하지 않는다 |
| `caller` | 하네스는 실행별 요약을 `runs/`에만 보관하고 `recording_status: pending_caller`로 반환한다. 해당 질문의 예정된 실행들이 끝난 뒤 외부 호출자가 원문 질문과 실제 종합 답변을 승인된 호출자 신원으로 한 번 저장한다 |

새 caller 대화는 공유 call_id로 공통 저장기를 호출하며 run_id 헤더를 넣지 않는다. 그 뒤 각 실행에 `python3 -m modules.harness.inspect_run <run_id> --attach-caller-dialog <saved-path>`를 실행해 같은 대화로 연결한다. 실행마다 연결 영수증을 남긴다. 실행 상태는 도구가 갱신하며 직접 수정하지 않는다. 원문·신원·content_id를 대조하고 나서 저장 완료로 표시한다. 검증은 실제로 화면에 전달됐다는 인증은 아니므로, 저장된 답변을 그대로 사용자에게 전달할 책임은 호출자에게 있다.

호출자의 저장이 실패하면 답변을 보존하고 같은 call_id로 저장만 다시 시도한 뒤 연결도 다시 시도한다. Harness의 저장 복구 명령은 이미 저장된 공유 대화를 찾아 연결할 수 있지만 실행 요약을 대신 Q/A로 저장하지 않는다. 연결되지 않은 기록은 계속 대기로 표시하며 작업 성공 여부와 대화 저장 완료를 구분한다. 최종 답변이 저장된 질문으로 새 실행을 시작하지 않으며 추가 작업은 새 사용자 요청으로 받는다.

내부 구현자·리뷰어에는 소유자와 관계없이 `LOG_BY_HARNESS=1`을 전달하여 dialog 저장을 생략한다. 사용자에게 답하는 외부 호출자는 caller 모드의 LOG-001 의무를 유지한다. 소유자 필드 도입 이전 실행은 당시 신원과 저장 복구 방식을 유지하며 기존 dialog·승인 파일을 이 정책으로 소급 변경하지 않는다.

## SHR-001. 공유 범위

- 실제 대화(인용·요약 포함), 승인·권한 추적, 실행 입력·출력·로그·상태 원본, 인증 정보, 개인 환경·계정·사용량, 내부 개발 메모는 로컬에 보관한다. 문서에 옮겨 적은 경우에도 같은 기준을 적용한다.
- 코드, 비밀값 없는 공통 설정, 합성 테스트·예제, 검토한 사용·설계·검증 문서는 공유한다. 공개 검증 요약에는 재현 가능한 결과와 한계를 설명하고, 개인 대화·계정 정보·개별 실행 식별자는 넣지 않는다.
- 기존 비공개 기록과 내부 milestone 문서는 공개를 위해 삭제하거나 다시 쓰지 않는다. 별도 공개 가이드를 작성한다. `.gitignore`에 나열한 `docs/`의 공개 가이드만 공유하며, 새 가이드를 추가할 때는 내용을 검토하고 목록도 갱신한다.
- `dialog/`, `approvals/`, `runs/`는 빈 `.gitkeep`만 공유한다. 실제 내용을 공개 문서나 fixture에 복사하지 않는다. 합성 예제와 경로·ID 자리표시자를 사용한다.
- 제외 규칙과 비밀값 검사는 모든 사적 정보를 판별하거나 이미 추적된 파일을 제거하지 않는다. 실제 공유 후보와 스테이징 내용을 확인한다. 공개 가이드는 제외된 내부 문서에 의존하지 않아야 한다. 로컬 LOG-001 기록은 계속한다.

## PRE-001. 우선순위

- 사용자의 명시적 지시가 없으면 이 규칙이 항상 적용된다.
- 사용자는 대화 저장 방식, 위치, 저장 여부를 명시적으로 바꿀 수 있다. 그런 지시가 없으면 LOG-001이 적용된다.

## LOOP-001. 하네스 loop 동작 (초기 규칙)

하네스가 AI를 호출할 때(run_id가 있을 때) 적용된다.

- 라운드 순서: 구현 → 하네스 검증 → 다른 도구의 리뷰 → 완료 또는 수정 후 반복.
- 한 작업 공간에서는 한 번에 한 구현자만 수정한다. 리뷰어는 파일을 수정하지 않으며, 쓰기 권한은 하네스 실행 설정으로 제거한다.
- 테스트 결과와 리뷰 승인은 같은 코드 상태에 대해서만 유효하다. 수정이 있으면 둘 다 다시 한다.
- 하네스는 최대 반복 수와 실행 시간을 강제한다. 실행 종료 상태는 `success`, `limit_reached`, `failed`, `waiting_for_user` 중 하나이며, 성공이 아닌 종료를 성공으로 보고하지 않는다.
- 실행 상태와 완료 판정은 하네스가 관리한다. AI는 구조화된 결과를 제출하고, 하네스는 대화 텍스트의 "완료했습니다"를 파싱하지 않는다.

## DOC-001. 어떤 AI가 어떻게 읽는가

| 도구 | 읽는 파일 | 비고 |
|---|---|---|
| Codex CLI | `AGENTS.md` | 인식한 프로젝트 루트(보통 Git 루트)부터 작업 디렉터리까지 탐색한다. 프로젝트 루트를 찾지 못하면 프로젝트 규칙은 현재 디렉터리에서만 확인한다 |
| Claude Code 2.1.277 이상 | `AGENTS.md` | 2.1.280에서 확인. `CLAUDE.md`가 있으면 그쪽이 우선. `--restricted` 사용 시 읽지 않음 |
| Gemini CLI | `GEMINI.md` (기본) | `context.fileName` 설정으로 `AGENTS.md`를 지정해야 읽는다 |
| Cursor, Copilot 등 | `AGENTS.md` | 도구별 지원 범위는 각 문서 확인 |

프로젝트 루트가 인식되지 않는 환경에서 Codex CLI를 직접 사용할 때에는 `loop_harness` 루트에서 시작하거나 루트 지침을 명시적으로 제공한다. 하위 디렉터리에서 시작했다는 이유만으로 루트 규칙이 자동 적용된다고 가정하지 않는다. [OpenAI 공식 설명](https://learn.chatgpt.com/docs/agent-configuration/agents-md)을 따른다.

하네스 호출은 `modules/harness/prompts.py`에서 지침을 별도로 수집하고 프롬프트로 전달한다. 수집 기준은 `loop_harness`가 아니라 **대상 작업 공간**이다. 대상 작업 공간과 그 상위 디렉터리, 하위 디렉터리의 `AGENTS.md`·`AGENTS.override.md`·`CLAUDE.md`를 모두 요구한다. 대상이 이 프로젝트 밖에 있으면 `loop_harness`의 `AGENTS.md`는 자동으로 포함되지 않으며, 역할 제약은 프롬프트에 직접 들어간다. 이 전달 경로는 CLI 자체의 자동 탐색과 구분한다.

하위 디렉터리를 탐색할 때에는 `.git`, `node_modules`, `__pycache__`, `.venv`라는 이름의 디렉터리를 제외하고, 디렉터리 심볼릭 링크는 따라가지 않는다. 위의 지침 요구는 이 탐색 범위에서 발견되는 파일에 적용된다. 이 제외 조건은 대상 작업 공간 자체와 상위 디렉터리를 확인하는 절차에는 적용되지 않는다.
